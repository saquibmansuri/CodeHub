KUBERNETES ARCHITECTURE

1. Master Node:
Acts as the control plane for the Kubernetes cluster, managing the overall state and configuration. It coordinates and schedules the execution of containers on worker nodes.

2. Worker Nodes:
Run the containerized applications in pods. They are controlled by the master node and include services like kubelet, kube-proxy, and container runtime.

-- In master node
3. Controller Manager:
Contains various controllers that regulate the state of the cluster, such as Node, ReplicaSet, and Deployment controllers. It ensures that the desired state matches the current state of the resources.
A controller is any process or code that runs in a loop and is continuously monitoring the k8s cluster and listening to events of specific objects being changed.

4. ETCD:
A highly available, distributed key-value store that stores all cluster data, including configuration, secrets, and the entire state of the Kubernetes cluster.

5. Kube-scheduler:
Determines the best available node for a pod based on factors like resource requirements, policies, and constraints, ensuring efficient utilization of resources.

6. Kube-apiserver:
Serves as the front end for the Kubernetes control plane, exposing the Kubernetes API. It validates and processes API requests, coordinating communication between various components.

-- In worker node
7. Kubelet:
Runs on each worker node, ensuring that containers defined in the pod specs are running and healthy. It interacts with the container runtime and monitors the state of the node.

8. Kube-proxy:
Manages network communication for services within and outside the cluster. It maintains network rules on nodes to route traffic to appropriate pods and ensure connectivity.

# TO VERIFY IF ROLE WAS CREATED OR NOT- kubectl get roles -n prod
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: prod
  name: prod-full-access
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]



# CREATE A ROLE BINDING FOR A PROD TEAM - kubectl apply -f rolebinding.yml
# TO VERIFY IF ROLEBINDING WAS CREATED  - kubectl get rolebindings --namespace=prod
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: prod-full-access-binding
  namespace: prod
subjects:
- kind: User
  name: prodteam
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: prod-full-access
  apiGroup: rbac.authorization.k8s.io



# CREATE A ROLE TO RESTRICT ACCESS TO NAMESPACE - kubectl apply -f restrictrole.yml
# TO VERIFY IF ROLE WAS CREATED OR NOT- kubectl get roles --namespace=prod
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: prod
  name: no-access
rules: []



# CREATE A ROLE BINDING FOR A USERS OTHER THAN PRODTEAM - kubectl apply -f restrictrolebinding.yml
# TO VERIFY IF ROLEBINDING WAS CREATED  - kubectl get rolebindings --namespace=prod
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deny-all-binding
  namespace: prod
subjects:
- kind: Group
  name: system:authenticated
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: no-access
  apiGroup: rbac.authorization.k8s.io

Feature              | LimitRange                          | ResourceQuota                      
---------------------|-------------------------------------|------------------------------------
Scope                | Individual containers or pods       | Entire namespace                   
Purpose              | Sets default/min/max per-container  | Limits total resource consumption  
                     | limits                              | across all pods in a namespace

                     | pod/container resource requests     | consumption                         
Example              | Default CPU/memory per container    | Maximum total CPU/memory for       
                     |                                     | namespace

                     |                                     | namespace

+ docker-registry   Create a secret for use with a Docker registry
+ generic           Create a secret from a local file, directory, or literal value
+ tls               Create a TLS secret


Examples:
  # Create a new secret named my-secret with keys for each file in folder bar
  kubectl create secret generic my-secret --from-file=path/to/bar
  
  # Create a new secret named my-secret with specified keys instead of names on disk

  # Create a new secret named my-secret with key1=supersecret and key2=topsecret

# TAINTS & TOLERATIONS IN KUBERNETES

taints and tolerations work together to ensure that pods are scheduled on appropriate nodes. This mechanism allows nodes to "repel" certain pods unless the pods explicitly tolerate the taints that the nodes have.

A taint is applied to a node and can repel a set of pods that do not tolerate that taint. Taints have three properties:
Key, Value & Effect

The effect can be one of the following:
NoSchedule: New Pods that do not tolerate this taint are not scheduled on the node. Pods already running on the node continue to run normally. 
PreferNoSchedule: Kubernetes will try to avoid placing a pod that does not tolerate this taint on the node but it's not a strict enforcement.
NoExecute: Pods that do not tolerate this taint will be evicted from the node if they are already running, and will not be scheduled on the node in the future. Strongest restriction. Blocks all new pods without a matching toleration.

EXAMPLE - kubectl taint node <node name> key1=value1:NoSchedule
This command applies a taint to node where the taint key is key1, the value is value1, and the effect is NoSchedule. This means that no pod that lacks a toleration for key1=value1:NoSchedule will be scheduled on node1.

A toleration is applied to a pod and allows (but does not require) the pod to schedule onto a node with matching taints. Tolerations are specified in the pod specification and consist of a key, value, and effect, which should match the key, value, and effect of the taint they are meant to tolerate.
This pod will tolerate the taint key1=value1:NoSchedule, allowing it to be scheduled on node1 despite the taint that repels other pods.
If the tolerance matches with the taint specified on the node, then only it will be allowed on that node, otherwise it will be scheduled on other nodes


EXAMPLE:
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
  - name: mycontainer
    image: myimage
  tolerations:
  - key: "key1"
    operator: "Equal"
    value: "value1"
    effect: "NoSchedule"


# TO REMOVE AN EXISTING TAINT FROM A NODE
kubectl taint nodes <NODE NAME> key1-

## Cluster Maintenance

# When you want to make OS upgrade or patch upgrade on node then before doing that its the best practice to drain that particular node, this deletes all pods and recreates them on another node. And draining also ensures that no pod is scheduled on this node in future until specified restriction is removed

kubectl drain node01
kubectl drain node01 --ignore-daemonsets
kubectl cordon node02    # this only stops future scheduling of pods on this node, existing ones will stay, draining before this command is best practice
kubectl uncordon node01  # to allow pods to be scheduled again on this node

# BACKUP & RESTORE KUBERNETES CLUSTER USING ETCD Cluster
References - https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/#backing-up-an-etcd-cluster
           - https://github.com/etcd-io/website/blob/main/content/en/docs/v3.5/op-guide/recovery.md
           - https://www.youtube.com/watch?v=qRPNuT080Hk

# BACKING UP
# Take snapshot of etcd server database (this contains information related to all existing resources)
# These 4 parameters - endpoint, cacert, cert and key are mandatory

-etcdctl version
-check image used by etcd pod in kube-system namespace by describing the pod
-describe etcd pod in kubesystem namespace and see '--key-file', '--listen-client-urls', '--peer-trusted-ca-file' & '--cert-file' as we would need these later in backup command

ETCDCTL_API=3 etcdctl --endpoints=https://[127.0.0.1]:2379 \
--cacert=/etc/kubernetes/pki/etcd/ca.crt \
--cert=/etc/kubernetes/pki/etcd/server.crt \
--key=/etc/kubernetes/pki/etcd/server.key \
snapshot save snapshot.db


# To view the status of the snapshot
ETCDCTL_API=3 etcdctl \
    snapshot status snapshot.db
 
# RESTORING
# First stop the kube-api server before restoring
service kube-apiserver stop
(if the above command doesnot work then move the kubeapi server manifest to some temporary location)
mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/
sleep 30

# Restore the snapshot (the --data-dir /var/lib/etcd-from-backup path can be anything inside /var/lib, dont use same as existing from describe pod output, because it needs empty directory upon every restore operation)
ETCDCTL_API=3 etcdctl \
  snapshot restore snapshot.db \
  --data-dir /var/lib/etcd-from-backup

# AFTER RESTORING UPDATE THIS FILE - /etc/kubernetes/manifests/etcd.yaml
We have now restored the etcd snapshot to a new path on the controlplane - /var/lib/etcd-from-backup, so, the change to be made in the YAML file, is to change the hostPath for the volume called 'etcd-data' from old directory (/var/lib/etcd) to the new directory (/var/lib/etcd-from-backup) and also the --data-directory value.
so in the file change all the '/var/lib/etcd' to '/var/lib/etcd-from-backup' (tip: there will be multiple occurances, approx 3)

# Reload the daemon
systemctl daemon-reload

# Restart etcd service
service etcd restart (although upon updating the manifest file as above it wwould auto restart)

# Atlast restart the kube-api server
service kube-apiserver start
(if the above command doesnot work then move BACK the kubeapi server manifest which we moved into tmp location)
mv /tmp/kube-apiserver.yaml /etc/kubernetes/manifests/

# restart other components if you want (OPTIONAL)
# Restart kube-controller-manager
mv /etc/kubernetes/manifests/kube-controller-manager.yaml /tmp/
sleep 20
mv /tmp/kube-controller-manager.yaml /etc/kubernetes/manifests/

# Restart kube-scheduler
mv /etc/kubernetes/manifests/kube-scheduler.yaml /tmp/
sleep 20
mv /tmp/kube-scheduler.yaml /etc/kubernetes/manifests/

# Restart kubelet
systemctl restart kubelet

# Certificate (Public key) naming has *.crt OR *.pem
example- server.crt, server.pem, client.crt, client.pem

# Private key naming has *.key OR *-key.pem
server.key

- Server certificates are certificates which stay with server components to serve requests to their clients by proving they are the real servers
- Client certificates are certificates which stay with client components to prove they are the real clients to the servers

# Server components in k8s having server certificates (bcz they expose api)
kubeapi-server, etcd & kubelet

# Client components (ones who use server components using their own client certificates)
human, scheduler, kube-controller-manager, kube-proxy

# KUSTOMIZE BASICS 
Kustomize is a Kubernetes-native configuration management tool that lets you customize raw, template-free YAML files across different environments (like Dev, Staging, and Prod) without modifying the original manifests. 
It uses a "base and overlay" approach, meaning you maintain a shared base configuration and layer environment-specific changes on top.
You write your resources once, and modify only what changes between environments

# TERMINOLOGIES IN KUSTOMIZE 
Kustomize organizes the manifests into a standard directory structure featuring Bases and Overlays:
- Base: A directory containing standard, environment-agnostic Kubernetes YAML files (e.g., deployment.yaml, service.yaml) alongside a kustomization.yaml file that lists them.
- Overlay: A directory that holds configurations specific to an environment (e.g., dev or prod). It contains its own kustomization.yaml pointing to the Base, along with patch files or configuration snippets that override specific fields (like replica counts, container images, or environment variables).
- Components; A Kustomize component is a modular, reusable building block of Kubernetes configurations (resources + patches) that you can optionally "opt-in" to include in selected environments.

# FOLDER STRUCTURE 
k8s/
  base/
    kustomization.yaml 
    deployment.yaml
    service.yaml
  overlays/
    dev/
      kustomization.yaml
      config-map.yaml
    staging/
      kustomization.yaml
      config-map.yaml
    prod/
      kustomization.yaml
      config-map.yaml
  components/
    component1/
      kustomization.yaml
      deployment.yaml
    component2/
      kustomization.yaml
      deployment.yaml

BASE + OVERLAYS + COMPONENTS = FINAL K8S MANIFESTS (CREATED BY KUSTOMIZE)

# Commands
- kustomize build k8s/ (path where the base manifest and kustomization.yaml resides, this only build, it doesn't apply anything)
--- apply with any one of these commands ---
- kustomize build k8s/ | kubectl apply -f -
- kubectl apply -k k8s/ 
--- delete with any one of these ---
- kustomize build k8s/ | kubectl delete -f -
- kubectl delete -k k8s/

# Common transformations
- commonLabel: adds a label to all the k8s resources
- namePrefix/Suffix: adds a common prefix/suffix to all resource names
- namespace: adds a common namespace to all resources
- commonAnnotations: adds an annotation to all resources

# Image transformers: replaces images in the k8s manifests

# Patches
- kustomize patches provides another method to modifying kubernetes configs 
- unlike common transformations, patches provides more surgical approach to targeting one or more specific sections in a k8s resource
- to create a patch 3 parameters should be provided
    - Operations type: add/remove/replace  (these are most common, but there are more available)
    - Target: what resource should this patch be applied on
        - kind
        - version/group
        - name
        - namespace
        - labelSelector
        - annotationSelector
    - Value: what will be the value that will either be replaced or added  (only needed for add/replace operations)

# COMPONENTS
- kustomize components provides ability to define reusable pieces of configuration logic (resources + patches) that can be included into multiple overlays
- components are useful in situations where applications support multiple optional features that need to be enabled only in a subset of overlays (we can simply put file in that particular overlay but its NOT good since again we will have to manage multiple copies, this is where components help us in reusability)

--- Application failure
-check labels of pods and deployments
-check node port, svc port and target port
-check selectors in svc
-describe and check env variables in pods/deployments
-describe and check password for mysql pod is present in environment variables (database name is not visible in pod logs, so ignore it)

--- Control plane failures
- check node status: kubectl get nodes
- check pod status: kubectl get pods
- check control plane pods: kubectl get pods -n kube-system
- check control plane and worker node services if not managed by kubeadm: service kube-apiserver status
- check logs of control plane service: kubectl logs <pod name> -n kube-system
- check logs of control plane and worker node service if not managed by kubeadm: sudo journalctl -u kube-apiserver
- check manifests here: /etc/kubernetes/manifests/
- check the volume mount path in manifest files at /etc/kubernetes/manifests

--- Worker node failures
- check nodes
- describe nodes
- check storage, memory, cpu by going in that particular node
- check kubelet service status in the node: service kubelet status
- check logs of the service in the node - sudo journalctl -u kubelet
- check kubelet certificates (check issuer, validity): openssl x509 -in /var/lib/kubelet/worker-1.crt -text
- check kubelet conf file issues: cat /var/lib/kubelet/config.yaml
- check kubelet.conf in node01, /etc/kubernetes/kubelet.conf
- control plane port: https://controlplane:6443

--- Network troubleshooting
- check service selectors, pod/deployment labels
- check coredns pod working or not: kubectl get pods -n kube-system | grep coredns
- verify kubedns endpoints: kubectl get endpointslice -l k8s.io/service-name=kube-dns -n kube-system
- check pod resolv.conf file: kubectl exec -it <pod_name> -- cat /etc/resolv.conf
- check if dns is working from a pod: kubectl exec -it busybox -- nslookup kubernetes.default.svc.cluster.local
- for network troubleshooting always go in this order: pods, service, coredns, cni, kube-proxy
- check cni: kubectl get pods -n kube-system | grep -E "calico|cilium|flannel|weave|aws-node|kube-router|kindnet"
- cni plugin directory: ls -la /etc/cni/net.d/
- check kubelet service logs and grep by cni: sudo journalctl -u kubelet | grep -i cni
- install cni plugin (flannel) if not initialized
- for kube proxy, first check the pod logs, then daemon set and configmap of kube-proxy


# Topic: Endpoint slicing
Why Do They Exist? (The Problem They Solve)
In older Kubernetes versions, a resource called Endpoints tracked every single pod IP for a service in one giant list.
* If a service had 5,000 pods and just one pod changed its IP, Kubernetes had to rewrite and resend the entire list of 5,000 IPs to every node in the cluster.
* This wasted massive amounts of network bandwidth and slowed down large clusters
EndpointSlices solve this by breaking that giant list into smaller, manageable pages (slices). By default, each slice caps out at 100 endpoints. If you add a 101st pod, Kubernetes simply creates a new slice instead of modifying the existing list.
